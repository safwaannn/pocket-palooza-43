Introduction

FinTrack is a full-stack personal finance management web application that helps an individual track income and expenses, plan monthly budgets, and understand exactly where their money goes — all from one private, role-aware dashboard. It is built as a classic three-tier system: a React 19 + Vite single-page front-end, a Node.js / Express REST API, and a MongoDB document database accessed through the Mongoose ODM.

There are two broad classes of actor in the system: the End User (who may hold the role viewer, user, or manager) and the Administrator. After registering with a name, email, and password, a user lands on a personal Dashboard that summarises the current month's income, expenses and balance, shows a budget-watch strip for every category, and lists recent transactions. From there the user can record income/expense transactions (individually or via CSV import), organise money into income/expense categories (system-provided defaults plus their own custom ones), set a monthly spending limit per category, and let the system watch that limit and raise an alert automatically at 80% and 100% of it. Recurring money movements — rent, salary, subscriptions — can be scheduled once and are then auto-posted as real transactions on their due date. A Calendar view surfaces every upcoming due date, and a Reports page turns the raw ledger into pie and bar charts. The Administrator, in turn, can see every user's aggregate totals and promote or demote a user's role.

Unlike a paper cash-book or a generic spreadsheet, FinTrack understands money as structured, queryable data: every rupee is tagged with a user, a category, a type (income/expense) and a date, which is what makes automatic budget tracking, multi-currency display, and instant reporting possible.

2

Problem Definition

Most individuals still track their personal finances using informal, error-prone methods — a notebook, a series of disconnected messaging app reminders, or a spreadsheet that is rebuilt every month. These methods share the same weaknesses:

  • There is no single place that shows income, expenses and balance together, so a person only discovers overspending after the money is already gone.
  • Recurring bills (rent, EMIs, subscriptions) are easy to forget because nothing proactively reminds the person before the due date.
  • A spreadsheet has no concept of a "budget limit" — nothing warns the user automatically when a category is close to, or has crossed, its planned limit.
  • Manually categorising and totalling hundreds of transactions to answer a simple question — "how much did I spend on food this month?" — is slow and repetitive.
  • Data kept in a personal file has no access control; it cannot safely be shared with a family member or an advisor who should only see limited, role-appropriate information.

FinTrack is defined to solve exactly this problem: a single, secure, always-available web system that records every transaction once, automatically classifies and totals it, actively watches budgets on the user's behalf, and presents the result as an easy-to-read dashboard and report — removing the manual bookkeeping effort entirely.

3

Current (Existing) System

Before adopting a system like FinTrack, the typical "current system" used by an individual to manage personal finance is entirely manual or semi-manual, and suffers from the following gaps:

  • Manual ledgers / notebooks — every entry is handwritten; there is no automatic total, no category-wise break-up, and no way to search past entries.
  • Generic spreadsheets — require the user to write and maintain their own formulas; a single wrong cell reference silently produces a wrong total, and there is no built-in alerting.
  • Standalone banking apps — show transactions for a single account/card only, and rarely let the user define custom budgets or categories that match their own spending habits.
  • No recurring-transaction memory — a person must remember, every single month, to log the rent payment, the salary credit, or a subscription renewal.
  • No role separation — a single shared account (e.g. a family spreadsheet) gives everyone full edit rights; there is no "read-only" or "admin" distinction.

These systems focus purely on recording a transaction; none of them proactively help the user understand, budget for, or get warned about their spending — the gap FinTrack is built to close.

4

Proposed System

Purpose

FinTrack is proposed as a secure, web-based, multi-user personal finance tracker that automates the entire cycle of recording income/expenses, organising them by category, enforcing monthly budgets, raising timely alerts, auto-posting recurring transactions, and visualising the result through charts — replacing every manual step described in the existing system.

Scope & Objectives

  • Allow a user to sign up, sign in, and manage a personal profile (name, email, password, preferred currency) securely.
  • Let a user record, edit, delete, search and filter income/expense transactions, and bulk import/export them via CSV.
  • Provide default global categories plus the ability to create custom income/expense categories.
  • Let a user set a monthly spending limit per category and automatically track spend against it.
  • Automatically raise a one-time alert when spend crosses 80% and 100% of a budget.
  • Schedule recurring transactions (daily / weekly / monthly / yearly) that auto-post on their due date and surface upcoming dues on a calendar.
  • Visualise income vs. expense trends and category-wise break-up through pie/bar reports.
  • Support role-based access (viewer, user, manager, admin) and an admin panel to view every user's totals and manage roles.

Functional Requirements

  • 1Authentication — signup, login, logout, forgot/reset password, change password.
  • 2Transaction management — create, read, update, delete; filter by type/category/date/keyword.
  • 3CSV import / export of transactions.
  • 4Category management — global defaults + custom, income or expense.
  • 5Budget management — one limit per category per month; live spent/remaining %.
  • 6Automatic alerting at 80% / 100% of budget, with acknowledge + optional email.
  • 7Recurring schedules — create/pause/edit; auto-materialise due transactions.
  • 8Calendar view of upcoming recurring dues.
  • 9Reports & dashboard — totals, monthly trend, category break-up.
  • 10Multi-currency display per user.
  • 11Admin panel — list users, view totals, change a user's role.

Non-Functional Requirements

  • Security — passwords hashed with bcrypt, JWT-based sessions, role-based route guards, password fields never sent to the client.
  • Data isolation — every query is scoped to the logged-in user's own _id.
  • Performance — compound MongoDB indexes on (user, date) and (user, active, next_run) keep the hottest queries fast as data grows.
  • Usability — responsive, single-page interface; instant client-side validation via Zod + React Hook Form.
  • Reliability — idempotent alert generation (unique index) guarantees no duplicate alerts.
  • Maintainability — modular Express routes/controllers/models; typed React components.
  • Availability — stateless API tier, horizontally scalable behind a load balancer.
5

Need of the Proposed System

A working individual today juggles multiple income sources, recurring bills, and discretionary spending across several payment modes (cash, UPI, card). Without a system that consolidates all of this, budgeting decisions are made on guesswork rather than data, and problems (like a category quietly going over budget) are noticed only after the fact. FinTrack is needed to give the user a live, always-accurate picture of their money, remove the manual effort of logging recurring bills every month, and turn budgeting from a reactive chore into a proactive, alert-driven habit.

Scope of the Proposed System

The system is designed for use by any individual who wants to track personal or household finances, and can be extended to small households or shared family budgets with minor modification (e.g. multiple members under one budget). Because currency is a per-user setting supporting INR, USD, EUR, GBP, JPY, AUD, CAD, SGD and AED, the same system serves users across regions without change. The role layer (viewer / user / manager / admin) means the same deployment can also serve a small team or advisory relationship, where one person has read-only visibility into another's finances. The CSV import/export feature means the system can absorb historical data from any bank statement or spreadsheet the user already has, and export data back out at any time for use elsewhere.

Fact Finding Techniques

1. Interview
Prospective users — students and working individuals who currently track expenses on paper or in spreadsheets — were informally interviewed about what frustrates them most about their current method. This surfaced the two most-requested features: automatic budget alerts and recurring-bill reminders.

2. Observation
The existing habits of a few sample users (a shared family spreadsheet, a notes-app expense list) were observed directly to understand real usage patterns — how often entries are made, which categories dominate spend, and where the manual process breaks down (e.g. forgetting to log a transaction for days).

3. Questionnaire
A short questionnaire on desired features (currency preference, need for CSV import, importance of email alerts) was circulated among peers; the results directly shaped the priority of the multi-currency and email-alert features implemented in the system.

4. Document / Record Review
Sample bank statements and UPI transaction exports were reviewed to design a CSV import format that a real user's existing data could map onto with minimal manual clean-up.

Feasibility Study

1. Technical Feasibility

The entire stack — React, Node.js, Express, MongoDB — is open-source, free to use, well documented, and runs on ordinary consumer hardware. No proprietary or licensed component is required, so the project is technically feasible to build and to host.

2. Economic Feasibility

Development uses free/open-source tools throughout; the only recurring cost in production is database and server hosting, both of which have generous free tiers suitable for a personal-scale application. The cost saved in manual bookkeeping time far outweighs this.

3. Operational Feasibility

The interface mirrors a familiar dashboard/ledger layout, requires no training, and every core action (add transaction, set budget) takes only a few clicks — making day-to-day operation realistic for a non-technical end user.

4. Schedule Feasibility

The modular design (independent models for users, categories, transactions, budgets, alerts, and recurring schedules) allowed each module to be built, tested and integrated incrementally within the semester's project timeline.

Hardware and Software Requirements

Hardware Requirements

  • Processor: Dual-core 2 GHz or above (Intel i3 / equivalent)
  • RAM: 4 GB minimum (8 GB recommended for development)
  • Storage: 500 MB free disk space for the application & dependencies
  • Internet connection: broadband, for client–server communication
  • Standard display, keyboard and mouse / touch input

Software Requirements

  • Front-end: React 19, Vite 8, TypeScript, Tailwind CSS v4, shadcn/ui (Radix UI), React Router v7, TanStack Query, React Hook Form + Zod, Recharts
  • Back-end: Node.js, Express.js (REST API)
  • Database: MongoDB with Mongoose ODM
  • Authentication: JSON Web Tokens (JWT), bcryptjs password hashing
  • Email service: SMTP / Resend (budget-alert emails)
  • Operating System: Windows / Linux / macOS (cross-platform)
  • Tools: VS Code, Postman, Git & GitHub, MongoDB Compass

Limitations

Although the proposed system fulfils its stated objectives, it has the following limitations:

  1. The system currently manages a single individual's finances per account; joint/shared household budgeting across multiple linked accounts is not yet supported.
  2. There is no direct bank / UPI API integration — transactions must be entered manually or imported via CSV rather than being fetched automatically.
  3. The recurring-transaction "materializer" must be triggered (manually or by a scheduler) rather than running as an always-on background cron job in the current build.
  4. Budget alerts are evaluated per category per month; there is no overall "total monthly budget" alert across all categories combined.
  5. The system has been tested with a limited volume of sample data and may need further load-testing before large-scale, multi-thousand-user deployment.
  6. Advanced features such as investment tracking, multi-currency conversion (rather than per-user display currency), and a native mobile app are planned but not yet implemented.
21

Conclusion

FinTrack successfully demonstrates a complete, secure, full-stack solution to the problem of manual, fragmented personal finance tracking. By modelling money as structured data — a user, a category, an amount, a type and a date — the system is able to automate everything that used to require manual effort: totals update instantly, budgets are watched continuously, alerts fire exactly once at the right threshold, and recurring bills post themselves on schedule.

The project also demonstrates sound software-engineering practice: the back-end enforces every business rule (password hashing, per-user data isolation, unique compound indexes to prevent duplicate budgets/alerts) at the model layer so it can never be bypassed by a route, while the front-end offers a clean, responsive, role-aware interface built from reusable components.

From the analysis of its objectives against the finished build, it can be concluded that FinTrack is a reliable, extensible, and genuinely useful personal-finance tool — one that reduces the manual work of bookkeeping to almost nothing while giving the user a far clearer, real-time view of their money than a notebook or spreadsheet ever could. The modular structure of its six data collections and REST API also means the system can be extended in the future — shared household budgets, bank-feed integration, or a mobile client — without redesigning the core.
